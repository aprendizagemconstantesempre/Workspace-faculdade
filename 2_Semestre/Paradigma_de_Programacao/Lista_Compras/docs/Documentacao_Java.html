2. Funcionamento do sistema

O Lista de Compras ajuda o usuário a organizar as compras da casa. Ele cadastra as listas (por exemplo, "Compras da semana"), os estabelecimentos onde costuma comprar, com os dias de promoção, e os produtos, com foto, descrição e unidade de medida. Depois ele monta a lista: escolhe a lista e, se quiser, o estabelecimento, e inclui os produtos com quantidade e valor. O sistema calcula o subtotal de cada item, o total de itens e o valor total da compra.

Em todas as telas de cadastro o usuário pode incluir, consultar, editar e excluir. Exclusões e a saída do sistema sempre pedem confirmação. Um cadastro que já está sendo usado em algum item não pode ser excluído. Todos os dados ficam gravados no arquivo dados/lista_compras.json e voltam quando o sistema é aberto de novo.

A aplicação roda offline, em Windows com Java instalado, para um único usuário e sem login.

6. Herança

A classe pai Cadastro guarda o que as três telas de cadastro têm em comum: o id, o nome e a regra de nome repetido. As filhas chamam o construtor do pai com super(id, nome) e acrescentam só o que é delas.

public abstract class Cadastro {
    private int id;
    private String nome;

    public boolean temMesmoNome(String outroNome) {
        return nome.trim().equalsIgnoreCase(outroNome.trim());
    }
    public abstract String getDetalhe();
    public abstract String getMensagemEmUso();
    public abstract boolean estaVinculadoA(ItemLista item);
}

public class Estabelecimento extends Cadastro {
    private List<DayOfWeek> diasPromocao;
    public Estabelecimento(int id, String nome, List<DayOfWeek> dias) {
        super(id, nome);                 // o pai guarda id e nome
        this.diasPromocao = organizarDias(dias);
    }
}

Benefício: a regra "o nome não pode se repetir, ignorando maiúsculas, minúsculas e espaços" (RN007, RN022 e RN037) foi escrita uma única vez, em temMesmoNome(), e as três classes a herdam. O método recusarNomeRepetido() do Repositorio recebe List<? extends Cadastro> e serve para os três tipos.

8. Fluxo da aplicação

  1. O Main chama o App, que carrega o JSON (ou cria o arquivo vazio) e abre o Menu.
  2. Cadastro: o usuário cadastra o estabelecimento "Mercado Central" (Ter, Sex), os produtos e a lista "Compras da semana".
  3. Consulta: as tabelas e os contadores mostram os registros; a lista aparece com "0 produtos — R$ 0,00".
  4. Movimentação: o botão Montar abre o Criar lista com a lista escolhida; o usuário inclui os itens e vê os totais (12 itens, R$ 92,00).
  5. Consulta de novo: de volta ao Cadastrar lista, a mesma linha mostra "3 produtos — R$ 92,00".
  6. Sair: confirma, grava o arquivo e fecha. Ao abrir de novo, os dados continuam lá.
Por que a Consulta não é uma tela separada: o documento de requisitos do grupo (trabalho de Processo de Software) define que o menu tem exatamente cinco opções (RN002) e que a consulta é exibida "na própria tela de cadastro, sem exigir uma ação extra do usuário" (RN010). Por isso a Consulta exigida pelo trabalho de Java fica embutida nas telas de cadastro (tabelas e cartões) e na tabela de itens do Criar lista (RF015).

11. Como executar

  1. Abrir a pasta Lista_Compras no IntelliJ IDEA (projeto Maven; o IntelliJ baixa JavaFX 21 e Gson sozinho).
  2. Executar a classe org.example.Main, ou rodar mvn javafx:run.
  3. Na primeira execução é criada a pasta dados com o arquivo lista_compras.json.

A classe Main não herda de Application de propósito: assim o JavaFX funciona mesmo estando no classpath, sem o erro "JavaFX runtime components are missing".
